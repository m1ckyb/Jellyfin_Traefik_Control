## Detailed Findings

### Finding 1: SSH Host Key Verification Disabled (Man-in-the-Middle Vulnerability)

- **File:** [routing.py](file:///home/michael/Traefik-Route-Control/routing.py#L133-L137) and [routing.py](file:///home/michael/Traefik-Route-Control/routing.py#L225-L229)
- **Function/Class:** `VPSManager.get_ssh_client()` / `VPSManager.test_connection()`
- **Severity:** 🔴 Critical
- **Category:** Security
- **Problem:** The Paramiko SSH client configuration uses `paramiko.WarningPolicy()` or automatically trusts unknown host keys. It does not enforce known host key verification.
- **Evidence:**
  ```python
  # routing.py:134-135
  # Fall back to WarningPolicy if no known_hosts file exists
  client.set_missing_host_key_policy(paramiko.WarningPolicy())
  ```
- **Impact:** An attacker who can perform ARP spoofing, DNS poisoning, or control a router on the path between the RouteGhost server and the target VPS can perform a Man-in-the-Middle (MitM) attack. They can intercept the SSH traffic, compromise the SSH credentials (such as the private key used for authentication), and execute arbitrary commands on the VPS or RouteGhost machine.
- **Attack Scenario:**
  An attacker intercepts the network routing to the VPS. When RouteGhost tries to connect via SSH to forward a port, the attacker presents their own SSH host key. Because `WarningPolicy` is active, RouteGhost accepts the key and proceeds to transmit authentication details, allowing the attacker to decrypt or hijack the connection.
- **How To Reproduce:**
  Change the VPS IP to point to a test server running an unauthorized SSH server. Observe that the SSH connection completes without any host key warning or failure.
- **Recommended Fix:**
  Require the user to provide the SSH Host Key Fingerprint during VPS setup. Verify this fingerprint explicitly during the connection phase instead of relying on `WarningPolicy()`.
- **Example Fix:**
  ```python
  # Load specific host key or match fingerprint:
  import binascii
  # Assuming stored_fingerprint is available
  host_key = client.get_host_keys().lookup(host)
  if host_key:
      key_fingerprint = binascii.hexlify(host_key.get_fingerprint()).decode()
      if key_fingerprint != stored_fingerprint:
          raise paramiko.SSHException("Host key verification failed.")
  ```

### Finding 2: Unsafe Shell Commands in Paramiko (Possible Command Injection)

- **File:** [routing.py](file:///home/michael/Traefik-Route-Control/routing.py#L198-L213)
- **Function/Class:** `VPSManager.cleanup_port_forward()`
- **Severity:** 🟠 Major
- **Category:** Security
- **Problem:** The `cleanup_port_forward` method parses rules from `iptables-save` using shell pipes (`| grep 'dport ...'`) and constructs rules to execute back on the SSH channel by modifying the string directly. If a rule containing special characters is injected into `iptables`, it can trigger command injection on the VPS.
- **Evidence:**
  ```python
  # routing.py:201
  stdin, stdout, stderr = client.exec_command(f"iptables-save | grep 'dport {s_public_port}'")
  ...
  # routing.py:210-212
  del_cmd = rule.replace("-A ", "-D ")
  cmd = f"iptables -t nat {del_cmd}"
  client.exec_command(cmd)
  ```
- **Impact:** Command execution on the remote VPS.
- **Attack Scenario:**
  If an attacker manages to modify iptables configurations on the VPS to include a rule containing a shell payload (e.g., adding a comment with backticks), when RouteGhost executes the cleanup command, it will parse that rule and pass it straight to the shell via `exec_command(cmd)`.
- **Recommended Fix:**
  Parse the rules locally in Python rather than passing raw strings back to a remote shell command. Execute iptables commands using parameterized list configurations or use a strict regex validation to make sure only standard flags and port formats are fed to `exec_command()`.
- **Example Fix:**
  ```python
  # Validate rule format before executing
  import re
  rule_pattern = re.compile(r"^-[AD] PREROUTING -p tcp -m tcp --dport \d+ -j DNAT --to-destination [\d\.:]+$")
  if rule_pattern.match(del_cmd.strip()):
      client.exec_command(f"iptables -t nat {del_cmd}")
  ```

### Finding 3: In-Memory Rate Limiting Dict Cache Leaks Memory

- **File:** [main.py](file:///home/michael/Traefik-Route-Control/main.py#L555-L557)
- **Function/Class:** `check_rate_limit()` fallback
- **Severity:** 🟡 Minor
- **Category:** Security / Backend Architecture
- **Problem:** The in-memory fallback rate limiter stores IP attempts in a global dictionary (`LOGIN_ATTEMPTS`) that grows indefinitely. There is no background task or eviction policy to remove inactive IP entries.
- **Evidence:**
  ```python
  # main.py:435-452 (referenced in fallback)
  LOGIN_ATTEMPTS = {}
  # ... keys are never popped or deleted, only their arrays are trimmed.
  ```
- **Impact:** An attacker who cycles through hundreds of thousands of IP addresses can cause the Python process memory usage to grow continuously, eventually causing an Out-Of-Memory (OOM) crash of the RouteGhost container.
- **How To Reproduce:**
  Send requests from 10,000 distinct IP addresses (e.g., via IP spoofing headers or simulated proxies). Observe the memory footprint of the Flask process.
- **Recommended Fix:**
  Store fallback IP limits in a size-limited cache (like `cachetools.TTLCache`) or enforce a maximum dictionary size.
- **Example Fix:**
  ```python
  from cachetools import TTLCache
  LOGIN_ATTEMPTS = TTLCache(maxsize=10000, ttl=300) # Evict after 5 mins
  ```

### Finding 4: Synchronous Blocking Remote API Calls (UniFi and Cloudflare)

- **File:** [main.py](file:///home/michael/Traefik-Route-Control/main.py#L1158)
- **Function/Class:** `toggle_unifi()`, `update_cloudflare_dns()`, `turn_on_service()`
- **Severity:** 🟠 Major
- **Category:** Backend Architecture
- **Problem:** When a user turns on a service, the backend makes synchronous, blocking HTTP API calls to external controllers (UniFi Controller, Cloudflare API, and VPS SSH). Flask blocks the request thread until these external systems respond, which can take 5–15 seconds.
- **Evidence:**
  ```python
  # main.py:1616-1919 in turn_on_service / toggle functions
  resp = session.put(url, json=payload, verify=verify_ssl, timeout=timeout)
  ```
- **Impact:** Concurrency bottleneck. If several users toggle services simultaneously, the web server thread pool will exhaust immediately, causing timeout errors (504 Gateway Timeout) for other users and blocking the entire UI.
- **Recommended Fix:**
  Use a task queue (like Celery, RQ, or a simple custom thread executor / background queue) to run the external interactions asynchronously. Immediately return a "pending" job ID to the frontend and poll for status.

### Finding 5: Single Worker Gunicorn Architecture

- **File:** [entrypoint.sh](file:///home/michael/Traefik-Route-Control/entrypoint.sh#L47)
- **Function/Class:** Gunicorn invocation
- **Severity:** 🟠 Major
- **Category:** Infrastructure / DevOps
- **Problem:** Gunicorn is started with `--workers 1`. While this prevents local multi-process database lock conflicts, it limits the application's throughput. If the single worker is blocked on a slow network call, the entire app freezes.
- **Evidence:**
  ```sh
  exec su-exec appuser:appgroup gunicorn \
    --bind 0.0.0.0:5001 \
    --workers 1 \
    --threads 4 \
  ```
- **Impact:** Slow responses and susceptibility to Denial of Service (DoS).
- **Recommended Fix:**
  Use multiple workers once the SQLite WAL mode is thoroughly battle-tested, or delegate all blocking operations to an asynchronous background worker process.

### Finding 6: No Database Backup or Restoration Strategy

- **File:** N/A (Missing System)
- **Severity:** 🟠 Major
- **Category:** Database
- **Problem:** There is no automated cron script, configuration, or utility to create periodic backups of the SQLite database (`config.db`).
- **Impact:** Data loss. In case of disk failure or volume corruption, all configured services, users, settings, and credentials will be lost.
- **Recommended Fix:**
  Provide a simple sqlite backup feature (e.g. `sqlite3 config.db ".backup 'config.db.bak'"`) run daily as a background cron job or expose it via the dashboard.

## Executive Summary

RouteGhost v0.2.1 is a self-hosted routing gateway that acts as a secure access manager for exposing local network services to the internet. 

**RouteGhost is NOT production-ready for paying customers.** 

While major improvements have been made since the previous audit (e.g., locked-down Docker files permissions, WAL database mode, and Redis rate limiters), severe production issues remain. Specifically, **SSH host key verification is completely disabled** during connection to the VPS, leaving the application open to Man-in-the-Middle (MitM) attacks. Additionally, the lack of an asynchronous task queue makes the application highly susceptible to thread exhaustion since calls to external UniFi and Cloudflare APIs block Flask requests synchronously.

## Scalability Assessment

- **100 users:** Responsive. A few seconds of delay during external configuration.
- **1,000 users:** Slower. Simultaneous rule creations will exhaust Gunicorn thread pools.
- **10,000 users:** Non-functional. The single Gunicorn worker blocks on network IO.
- **100,000+ users:** Immediate denial of service and OOM crash risks.

## Final Verdict

**HIGH RISK**

The application has resolved the major system vulnerabilities found in v0.1.2 (such as directory permissions and configuration whitelists). However, due to critical vulnerabilities like disabled SSH host key verification and severe backend execution bottlenecks, it is highly vulnerable to network attacks and denial of service. It should not be released to paying customers before addressing the blockers listed above.
