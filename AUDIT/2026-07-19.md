# Traefik-Route-Control (RouteGhost) — Production Readiness Audit

**Date:** 2026-07-19
**Version:** 0.1.2
**Auditors:** Security Engineer, Backend Architect, Frontend Engineer, DevOps Engineer, QA Engineer, Database Engineer, AI/LLM Security Engineer

---

## Executive Summary

This audit evaluates Traefik-Route-Control (RouteGhost) v0.1.2, a Flask-based web application that manages Traefik reverse proxy routes via Redis, UniFi firewall port forwarding, Cloudflare DNS/Origin Rules, WireGuard VPN routing, and Home Assistant MQTT discovery. The application supports passkey (WebAuthn), password, and TOTP 2FA authentication, with API key access for programmatic use.

**The application is NOT production-ready in its current state.** The panel identified 44 findings across 7 categories, including 4 Critical severity issues, 16 Major issues, and 24 Minor issues. The most dangerous vulnerabilities are: (1) `chmod 777` on the data directory exposing the Flask secret key and SQLite database to all container processes, (2) API settings endpoints that bypass the `ALLOWED_USER_SETTINGS` whitelist entirely, allowing any authenticated user to overwrite sensitive credentials like `UNIFI_PASS` and `VPS_SSH_KEY`, (3) identical whitelist bypass in the settings restore endpoint, and (4) no rate limiting on the 2FA verification endpoint enabling brute-force of 6-digit TOTP codes. Additionally, the application has no CI/CD pipeline, no security headers, no session timeout configuration, no graceful shutdown handling, and a single-gunicorn-worker architecture that creates both availability and concurrency limitations.

The application demonstrates good foundational intent — CSRF protection, passkey support, environment variable fallbacks, and Docker best practices with su-exec — but the implementation gaps are significant enough to constitute production blockers. The panel recommends a 30-day remediation plan before any public-facing deployment.

## Detailed Findings

### Finding 1: `chmod -R 777 /app/data` Exposes All Secrets

- **File:** `entrypoint.sh:31`
- **Function/Class:** Shell entrypoint script
- **Severity:** 🔴 CRITICAL
- **Category:** Security
- **Problem:** The entrypoint script runs `chmod -R 777 /app/data`, which grants world-readable, world-writable, and world-executable permissions to the entire data directory. This directory contains `config.db` (all user credentials, API keys, settings), `.secret_key` (Flask session signing key), and `app.log` (which may contain sensitive information).
- **Evidence:**
  ```sh
  # entrypoint.sh:31
  chmod -R 777 /app/data > /dev/null 2>&1
  ```
- **Impact:** Any process running inside the container — including any future add-on, sidecar, or compromised dependency — can read the Flask secret key and forge arbitrary user sessions. It can also read or modify the SQLite database directly, bypassing all authentication.
- **Attack Scenario:** An attacker who gains code execution inside the container (e.g., via a supply-chain attack on a Python dependency) reads `/app/data/.secret_key`, then crafts a Flask session cookie for any user, gaining full admin access.
- **How To Reproduce:** Run `ls -la /app/data/` inside the container after startup. All files show `-rwxrwxrwx`.
- **Recommended Fix:** Remove the `chmod 777` line entirely. The `chown` on lines 29-30 is sufficient when the correct PUID/PGID are used. If WSL2 permission issues exist, document them as a known limitation rather than using world-writable permissions.
- **Example Fix:**
  ```sh
  # entrypoint.sh — remove chmod 777, keep chown
  chown -R appuser:appgroup /app > /dev/null 2>&1
  chown -R appuser:appgroup /app/data > /dev/null 2>&1
  # chmod -R 777 /app/data > /dev/null 2>&1  # REMOVED
  ```

### Finding 2: Flask Secret Key Stored in World-Readable Directory

- **File:** `main.py:1968-1975`
- **Function/Class:** Module-level secret key initialization
- **Severity:** 🔴 CRITICAL
- **Category:** Security
- **Problem:** The Flask secret key is stored at `/app/data/.secret_key`. Combined with Finding 1 (`chmod 777`), any process in the container can read this file and forge session cookies.
- **Evidence:**
  ```python
  # main.py:1968-1975
  SECRET_KEY_FILE = os.path.join(DATA_DIR, '.secret_key')
  if os.path.exists(SECRET_KEY_FILE):
      with open(SECRET_KEY_FILE, 'rb') as f:
          app.secret_key = f.read()
  else:
      app.secret_key = os.urandom(24)
      with open(SECRET_KEY_FILE, 'wb') as f:
          f.write(app.secret_key)
  ```
- **Impact:** Session forgery. An attacker with file read access can impersonate any user including admin.
- **Attack Scenario:** Container compromise → read `.secret_key` → craft Flask session cookie → full admin access.
- **How To Reproduce:** `cat /app/data/.secret_key` inside the container.
- **Recommended Fix:** Use environment variables for the secret key (`SECRET_KEY` env var), or if file-based, ensure proper file permissions (0600) and store outside the world-writable directory.
- **Example Fix:**
  ```python
  # Prefer environment variable
  app.secret_key = os.environ.get('SECRET_KEY') or os.urandom(24)
  if 'SECRET_KEY' not in os.environ:
      SECRET_KEY_FILE = os.path.join(DATA_DIR, '.secret_key')
      if os.path.exists(SECRET_KEY_FILE):
          with open(SECRET_KEY_FILE, 'rb') as f:
              app.secret_key = f.read()
      else:
          with open(SECRET_KEY_FILE, 'wb') as f:
              f.write(app.secret_key)
      # Fix permissions
      os.chmod(SECRET_KEY_FILE, 0o600)
  ```

### Finding 3: In-Memory Rate Limiting Lost on Restart

- **File:** `main.py:435-452`
- **Function/Class:** `check_rate_limit()`
- **Severity:** 🟠 MAJOR
- **Category:** Security
- **Problem:** The `LOGIN_ATTEMPTS` dictionary is in-memory only. Every time the application restarts (deploy, crash, container restart), all rate-limit state is cleared. An attacker can force a restart or wait for scheduled restarts to reset their brute-force budget.
- **Evidence:**
  ```python
  # main.py:435-452
  LOGIN_ATTEMPTS = {}
  
  def check_rate_limit(ip_address, limit=5, window=60):
      """Simple in-memory rate limiting."""
      current_time = time.time()
      if ip_address not in LOGIN_ATTEMPTS:
          LOGIN_ATTEMPTS[ip_address] = []
      LOGIN_ATTEMPTS[ip_address] = [t for t in LOGIN_ATTEMPTS[ip_address] if current_time - t < window]
      if len(LOGIN_ATTEMPTS[ip_address]) >= limit:
          return False
      LOGIN_ATTEMPTS[ip_address].append(current_time)
      return True
  ```
- **Impact:** Rate limiting is effectively bypassable by restarting the application.
- **Attack Scenario:** Attacker makes 5 login attempts, restarts the app (or waits for a restart), gets 5 more attempts. Repeat indefinitely.
- **How To Reproduce:** Make 5 attempts → get 429 → restart container → make 5 more attempts → succeed.
- **Recommended Fix:** Use Redis-backed rate limiting (Redis is already a dependency) or a proper library like `flask-limiter`.
- **Example Fix:**
  ```python
  def check_rate_limit(ip_address, limit=5, window=60):
      """Redis-backed rate limiting."""
      r = get_redis()
      if not r:
          return True  # Fail open if Redis unavailable
      key = f"rate_limit:login:{ip_address}"
      try:
          current = r.get(key)
          if current and int(current) >= limit:
              return False
          pipe = r.pipeline()
          pipe.incr(key)
          pipe.expire(key, window)
          pipe.execute()
          return True
      except Exception:
          return True
  ```

### Finding 4: No Rate Limiting on 2FA Endpoint

- **File:** `main.py:2439-2474`
- **Function/Class:** `login_2fa()`
- **Severity:** 🟠 MAJOR
- **Category:** Security
- **Problem:** The `/auth/login/2fa` endpoint has no rate limiting. An attacker who knows a username and password can brute-force the 6-digit TOTP code (1,000,000 possibilities) or the 10-character hex recovery codes.
- **Evidence:**
  ```python
  # main.py:2439-2474
  @app.route('/auth/login/2fa', methods=['POST'])
  def login_2fa():
      """Verify 2FA code after password check."""
      # No rate limiting check here!
      user_id = session.get('pre_2fa_user_id')
      ...
      totp = pyotp.TOTP(user['totp_secret'])
      if totp.verify(code):
          login_user(User(user['id'], user['username']))
          ...
  ```
- **Impact:** Brute-force of TOTP codes. A 6-digit code has only 1M combinations. At 100 requests/second, that's ~2.8 hours to exhaust the space. Recovery codes (10 hex chars, ~1M combinations) are equally vulnerable.
- **Attack Scenario:** Attacker obtains valid password via phishing/breach → submits POST to `/auth/login/2fa` with randomized codes → eventually guesses the correct code → full account takeover.
- **How To Reproduce:** `for i in $(seq 1 1000000); do curl -X POST /auth/login/2fa -d "{\"code\":\"$(printf '%06d' $i)\"}" -H "Content-Type: application/json" -b "session=<cookie>"; done`
- **Recommended Fix:** Add rate limiting to the 2FA endpoint. Use account-based limiting (not just IP) since the user_id is in the session.
- **Example Fix:**
  ```python
  @app.route('/auth/login/2fa', methods=['POST'])
  def login_2fa():
      user_id = session.get('pre_2fa_user_id')
      if not user_id:
          return jsonify({"error": "Session expired"}), 400
      
      # Rate limit: 5 attempts per 5 minutes per user
      if not check_rate_limit(f"2fa:{user_id}", limit=5, window=300):
          return jsonify({"error": "Too many attempts. Please try again in 5 minutes."}), 429
      ...
  ```

### Finding 6: 2FA Disable Without Re-Authentication

- **File:** `main.py:2639-2645`
- **Function/Class:** `disable_2fa()`
- **Severity:** 🟠 MAJOR
- **Category:** Security
- **Problem:** Any authenticated user can disable 2FA without re-entering their password or providing a TOTP code. The code even contains a comment acknowledging this weakness.
- **Evidence:**
  ```python
  # main.py:2639-2645
  @app.route('/auth/2fa/disable', methods=['POST'])
  @login_required
  def disable_2fa():
      """Disable 2FA for current user."""
      # In a production app, you might want to require a password/code check here
      db.update_user_totp(current_user.id, None)
      return jsonify({"success": True})
  ```
- **Impact:** An attacker with a stolen session cookie (or XSS exploit) can disable 2FA, then use password-only login to persist access.
- **Attack Scenario:** Attacker steals session via XSS → disables 2FA → logs out victim → logs in with password only → persistent access.
- **How To Reproduce:** While logged in, `curl -X POST /auth/2fa/disable` — 2FA is immediately disabled.
- **Recommended Fix:** Require password re-entry and/or current TOTP code to disable 2FA.
- **Example Fix:**
  ```python
  @app.route('/auth/2fa/disable', methods=['POST'])
  @login_required
  def disable_2fa():
      data = request.get_json(silent=True) or {}
      password = data.get('password')
      code = data.get('code')
      
      user = db.get_user(current_user.id)
      
      # Require password
      if not password or not check_password_hash(user.get('password_hash', ''), password):
          return jsonify({"error": "Invalid password"}), 400
      
      # Require current TOTP code if 2FA is enabled
      if user.get('totp_secret'):
          if not code:
              return jsonify({"error": "2FA code required to disable 2FA"}), 400
          totp = pyotp.TOTP(user['totp_secret'])
          if not totp.verify(code):
              return jsonify({"error": "Invalid 2FA code"}), 400
      
      db.update_user_totp(current_user.id, None)
      return jsonify({"success": True})
  ```

### Finding 7: Password Reset Logs Plaintext Password

- **File:** `main.py:3384-3409`
- **Function/Class:** `api_reset_password()`
- **Severity:** 🟠 MAJOR
- **Category:** Security
- **Problem:** The password reset endpoint generates a random password and logs it in plaintext via `print()`. Since stdout/stderr are tee'd to `app.log`, anyone with access to the log file obtains the user's new password.
- **Evidence:**
  ```python
  # main.py:3403-3405
  print(f"\n🔐 PASSWORD RESET FOR USER: {username}")
  print(f"   New Password: {password}")
  print(f"   (This will only be shown once in the logs)\n")
  ```
- **Impact:** Credentials exposure. Anyone with log access (DevOps, log aggregation systems, shared volumes) obtains the plaintext password.
- **Attack Scenario:** DevOps engineer reads logs for debugging → sees password → uses it to impersonate user.
- **How To Reproduce:** Call `POST /api/users/<username>/reset-password` → check `app.log` → password visible.
- **Recommended Fix:** Return the password in the API response only (over HTTPS), never log it. Use a single-use token mechanism instead.
- **Example Fix:**
  ```python
  # Never log the password
  print(f"🔐 Password reset for user: {username}")
  # Return password to the API caller only (over HTTPS)
  return jsonify({"message": "Password reset successfully", "password": password})
  ```

### Finding 8: API Key Bypasses CSRF Protection

- **File:** `main.py:1949-1965`
- **Function/Class:** `check_csrf_protection()`
- **Severity:** 🟡 MINOR
- **Category:** Security
- **Problem:** Requests with the `X-API-Key` header skip CSRF protection entirely. While browsers cannot send custom headers in cross-origin requests without CORS preflight, this assumes the API key is secret. If an API key leaks, an attacker can forge state-changing requests without CSRF tokens.
- **Evidence:**
  ```python
  # main.py:1949-1965
  @app.before_request
  def check_csrf_protection():
      if request.method in ["POST", "PUT", "PATCH", "DELETE"]:
          if request.headers.get('X-API-Key'):
              return  # Skip CSRF for API key requests
          csrf.protect()
  ```
- **Impact:** If an API key is leaked, CSRF protection is entirely bypassed for all endpoints.
- **Attack Scenario:** API key leaks via log exposure → attacker sends cross-origin requests with the key → state changes without CSRF validation.
- **How To Reproduce:** Set up a page that sends `fetch('/api/settings', {method:'POST', headers:{'X-API-Key':'stolen-key'}, ...})` → CSRF succeeds.
- **Recommended Fix:** This is acceptable if API keys are truly secret and treated as bearer tokens. Add a warning comment and ensure API keys are rotated regularly. Consider adding origin validation.
- **Example Fix:**
  ```python
  @app.before_request
  def check_csrf_protection():
      if request.method in ["POST", "PUT", "PATCH", "DELETE"]:
          api_key = request.headers.get('X-API-Key')
          if api_key:
              # API key acts as bearer token — CSRF bypass is intentional
              # but ensure the key is validated before processing
              return
          csrf.protect()
  ```

### Finding 9: No Password Complexity Requirements

- **File:** `main.py:2486-2487`
- **Function/Class:** `change_password()`
- **Severity:** 🟠 MAJOR
- **Category:** Security
- **Problem:** Password validation only checks `len >= 8`. No requirements for uppercase, lowercase, numbers, or special characters. Users can set passwords like `aaaaaaaa` or `12345678`.
- **Evidence:**
  ```python
  # main.py:2486-2487
  if len(new_password) < 8:
      return jsonify({"error": "Password must be at least 8 characters"}), 400
  ```
- **Impact:** Weak passwords are trivially brute-forceable.
- **Attack Scenario:** User sets password `password` → attacker tries common passwords → gains access.
- **How To Reproduce:** `POST /auth/password/change` with `{"new_password": "aaaaaaaa"}` → succeeds.
- **Recommended Fix:** Add complexity requirements or use a zxcvbn-style strength check.
- **Example Fix:**
  ```python
  import re
  
  def validate_password_strength(password):
      errors = []
      if len(password) < 12:
          errors.append("at least 12 characters")
      if not re.search(r'[A-Z]', password):
          errors.append("an uppercase letter")
      if not re.search(r'[a-z]', password):
          errors.append("a lowercase letter")
      if not re.search(r'\d', password):
          errors.append("a number")
      if not re.search(r'[!@#$%^&*(),.?\":{}|<>]', password):
          errors.append("a special character")
      return errors
  ```

### Finding 10: API Settings Endpoint Bypasses ALLOWED_USER_SETTINGS Whitelist

- **File:** `main.py:3468-3480`
- **Function/Class:** `api_save_setting()`
- **Severity:** 🔴 CRITICAL
- **Category:** Security
- **Problem:** The `/api/settings` POST endpoint saves any key-value pair without checking the `ALLOWED_USER_SETTINGS` whitelist defined at `main.py:2710-2719`. An authenticated user can set `UNIFI_PASS`, `VPS_SSH_KEY`, `CF_API_TOKEN`, or any other sensitive setting.
- **Evidence:**
  ```python
  # main.py:3468-3480
  @app.route('/api/settings', methods=['POST'])
  @login_required
  def api_save_setting():
      """Save a single setting."""
      data = request.get_json()
      if not data or 'key' not in data or 'value' not in data:
          return jsonify({"error": "Invalid request data"}), 400
      
      try:
          db.set_setting(data['key'], data['value'])  # NO WHITELIST CHECK!
          return jsonify({"message": f"Setting '{data['key']}' saved successfully"})
      except Exception as e:
          return jsonify({"error": str(e)}), 500
  ```
  The whitelist is defined but never used:
  ```python
  # main.py:2710-2719
  ALLOWED_USER_SETTINGS = {
      'CF_API_TOKEN', 'CF_ZONE_ID', 'DOMAIN_ROOT', 'ORIGIN_RULE_NAME',
      'REDIS_HOST', 'REDIS_PORT', 'REDIS_PASS',
      'UNIFI_HOST', 'UNIFI_USER', 'UNIFI_PASS', 'UNIFI_RULE_NAME',
      ...
  }
  ```
- **Impact:** Any authenticated user can overwrite critical system settings including database credentials, API tokens, and SSH keys, potentially gaining full infrastructure access.
- **Attack Scenario:** Low-privilege user logs in → sends `POST /api/settings {"key": "UNIFI_PASS", "value": "hacked"}` → overwrites UniFi password → gains network equipment access.
- **How To Reproduce:** `curl -X POST /api/settings -d '{"key":"VPS_SSH_KEY","value":"malicious_key"}' -H "Content-Type: application/json" -b "session=<cookie>"`
- **Recommended Fix:** Add whitelist validation before saving any setting.
- **Example Fix:**
  ```python
  @app.route('/api/settings', methods=['POST'])
  @login_required
  def api_save_setting():
      data = request.get_json()
      if not data or 'key' not in data or 'value' not in data:
          return jsonify({"error": "Invalid request data"}), 400
      
      key = data['key']
      if key not in ALLOWED_USER_SETTINGS:
          return jsonify({"error": f"Setting '{key}' is not user-modifiable"}), 403
      
      try:
          db.set_setting(key, data['value'])
          return jsonify({"message": f"Setting '{key}' saved successfully"})
      except Exception as e:
          return jsonify({"error": str(e)}), 500
  ```

### Finding 11: Settings Restore Lacks Whitelist Validation

### Finding 37: No Graceful Shutdown

- **File:** `main.py:3743-3751`
- **Function/Class:** Background thread management
- **Severity:** 🟠 MAJOR
- **Category:** Reliability
- **Problem:** Background threads are daemon threads with no signal handling for graceful shutdown. On SIGTERM (Docker stop), threads are killed immediately, potentially in the middle of critical operations like port rotation or DNS updates.

  ```python

          perform_health_check()
          shutdown_event.wait(timeout=interval)
  
  def handle_shutdown(signum, frame):
      print("Received shutdown signal, stopping...")
      shutdown_event.set()
  
  signal.signal(signal.SIGTERM, handle_shutdown)
  signal.signal(signal.SIGINT, handle_shutdown)
  ```

## Final Verdict

**CONDITIONALLY NOT PRODUCTION-READY**

The Traefik-Route-Control (RouteGhost) v0.1.2 application demonstrates good architectural intent with its use of modern authentication methods (WebAuthn, TOTP), CSRF protection, and Docker best practices. However, the implementation has critical security vulnerabilities that must be resolved before any public-facing deployment:

1. **The settings whitelist bypass (Findings 10, 11) is a showstopper.** Any authenticated user can overwrite all system credentials, making this a full system compromise vector.

2. **The `chmod 777` + secret key exposure (Findings 1, 2) is a critical authentication bypass.** Session forgery is trivial for any process with container access.

3. **The missing rate limiting on 2FA (Finding 4) allows brute-force attacks** that completely undermine the second factor of authentication.

4. **The lack of security headers and session cookie hardening (Findings 42, 43)** leaves the application vulnerable to standard web attacks.

**Recommendation:** Do NOT deploy this application to any public-facing or sensitive environment until Week 1 of the remediation plan is complete (critical security fixes). The application may be suitable for isolated, trusted network use with the understanding that the security limitations exist, but should not be exposed to the internet or untrusted users.

**Timeline to production readiness:** 30 days with dedicated engineering effort as outlined in the remediation plan.
